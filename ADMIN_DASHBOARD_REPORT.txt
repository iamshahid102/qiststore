4. API REFERENCE (all under /api/v1/admin)
--------------------------------------------------------------------------------
Auth: Authorization: Bearer <access token>; role must be admin or staff.
Money: integer PAISA everywhere (Rs 1 = 100 paisa). UI converts rupees ↔ paisa.

DASHBOARD
  GET    /stats
         totals, pendingVerification, statusCounts, lowStockCount,
         salesSeries[14], recentOrders, topProducts, lowStock

PRODUCTS
  GET    /products?q=&status=&category=&stock=&sort=&page=&limit=
  GET    /products/:idOrSlug
  POST   /products                    (201 → { id, slug, sku })
  PATCH  /products/:idOrSlug          (partial; plans/cashPrice recompute minAdvance)
  DELETE /products/:idOrSlug          (archive by default)
  DELETE /products/:idOrSlug?permanent=true
                                      (409 if any order references it)
  PATCH  /products/:idOrSlug/stock    ({ qty, status?, track? })

REFERENCE DATA
  GET    /categories                  (flat, parent name, productCount)
  GET    /brands

ORDERS
  GET    /orders?q=&status=&paymentMethod=&from=&to=&sort=&page=&limit=
         meta.statusCounts included for the tabs
  GET    /orders/export.csv?status=   (text/csv attachment)
  GET    /orders/:orderNumber         (full doc + allowedTransitions + payments)
  PATCH  /orders/:orderNumber/status                  ({ status, note? })
  PATCH  /orders/:orderNumber/verification            ({ decision, reason? })
  PATCH  /orders/:orderNumber/notes                   ({ notes })
  PATCH  /orders/:orderNumber/schedule/:installmentNo
         ({ status, paidAmount?, method?, txnRef? })

CUSTOMERS
  GET    /customers?q=&status=&page=&limit=
  GET    /customers/:id               (profile + all linked orders + stats)
  PATCH  /customers/:id               ({ name?, email?, status?, role? })

SESSION
  GET    /me                          (verifies the signed-in staff member)

UPLOADS (existing, now used by the dashboard)
  POST   /uploads                     multipart field "file" → Cloudinary
  DELETE /uploads?publicId=
  GET    /uploads/status

ERROR BEHAVIOUR
  400 validation / business-rule error
  401 missing or expired token (client refreshes once, then redirects to login)
  403 customer/vendor token, or staff trying to change a role
  404 unknown order/product/customer
  409 duplicate slug/SKU, illegal order transition, or permanent delete of an
      order-linked product

5. BUSINESS RULES ENFORCED
--------------------------------------------------------------------------------
  • Advance ≥ 10% of cash price, advance < 2× cash price (shared engine).
  • monthly > 0 and an allowed term (3/6/9/12/18/24).
  • minAdvance is derived from the cheapest active plan — never hand-typed.
  • Slugs are normalised and unique; SKUs auto-generated with `QS-...`.
  • Product updates are partial-safe: patching `featured` does NOT wipe plans,
    images, specs or highlights (dedicated update schema).
  • Orders follow the state machine:
      pending_verification → verification_in_progress | approved | rejected | cancelled
      verification_in_progress → approved | rejected | cancelled
      approved → processing | cancelled
      processing → shipped
      shipped → delivered
      delivered → completed | defaulted
      rejected / completed / cancelled / defaulted → final
    Any illegal move is a 409 with a clear message.
  • Verification rejection requires a reason and writes it to the order.
  • Installment "paid" stores paidAt + paidAmount = amount; "partial" requires
    0 < paidAmount < amount; "reset" clears paidAt/paidAmount.
  • Blocking a customer increments tokenVersion (refresh tokens revoked).
  • Admin/staff cannot block themselves; only role=admin can change roles.

--------------------------------------------------------------------------------
6. SECURITY MODEL
--------------------------------------------------------------------------------
  • Server is the source of truth: every admin route re-checks the JWT and role.
  • The dashboard gate is a UX layer only; hiding buttons is never the boundary.
  • Access tokens live 15 minutes (ACCESS_TOKEN_TTL), refresh cookie 7 days.
  • admin-api.ts retries one 401 through /auth/refresh, updates localStorage,
    and only then redirects to /account/login?next=...
  • Login `?next=` accepts same-site paths only (no open redirect).
  • Role changes take effect on the next login because role is inside the JWT.
  • Validation with Zod on every write endpoint; ObjectIds validated.
  • Duplicate-key races return 409 instead of a 500.
  • Cloudinary upload endpoint keeps the existing 5 MB / MIME restrictions.
  • Role changes are audited by the normal API logs; order actions are written to
    the order timeline (visible in the UI).

11. KNOWN LIMITATIONS / NEXT STEPS
--------------------------------------------------------------------------------
  • Dashboard access control client-side gate hai; asli security server-side 403
    hai. Agar browser-level protection chahiye to httpOnly cookie + Next
    middleware based session add karna hoga.
  • Role change ke baad user ko dobara login karna hota hai (JWT mein role).
  • Categories, brands, deals, home rails aur CMS pages abhi read-only hain —
    unke CRUD endpoints/UI is scope mein nahi thay.
  • Detaching an image from a product does not delete the Cloudinary asset
    (orphan cleanup job recommended).
  • Refunds/returns, payment gateway reconciliation, courier tracking API,
    invoice PDFs and SMS/email notifications are not part of this scope.
  • No admin 2FA, password reset flow, or customer account creation by admin.
  • Revenue KPI = advances on approved+ orders; it is not accounting profit.
  • Customer table excludes staff/admin accounts by design.
  • No real-time push; use the Refresh button for new orders.
