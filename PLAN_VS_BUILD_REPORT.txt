3. WHAT DEVIATED FROM THE PLAN (and why)
--------------------------------------------------------------------------------

3.1 Installment schedule stored EMBEDDED in the order (plan §5.2 proposed a
    separate InstallmentSchedule collection). Embedded subdocuments keep the
    order document atomic (one write per state change), remove a join on the
    tracking path, and are fully sufficient for the implemented flows. For
    payment-collection scale (indexed queries across all orders, per-month
    reporting) promote it to its own collection — the DTO shapes stay the same.

3.2 Cart lives on the client (zustand + localStorage) instead of a server-side
    Cart collection with guest-id merging. Server trust is preserved because
    POST /checkout/quote and POST /checkout/order re-price and re-validate every
    line from the database. A server cart is only needed for cross-device
    persistence.

3.3 No separate `shared/` workspace package for zod schemas + DTO types. With a
    single API consumer, duplicating the DTO types in `client/src/types/api.ts`
    was simpler than a third workspace; unify when a second client (mobile app)
    appears.

3.4 Spec filters (RAM/Storage) — the plan's category sidebar. Filter DEFINITIONS
    are seeded and served via GET /facets/:categorySlug, and products carry the
    specs, but the sidebar currently exposes category / brand / advance-price /
    sort only, i.e. spec facets are not yet wired end-to-end.

3.5 Product images are gradient placeholders (deterministic per product name)
    for the SEEDED catalogue, so the repo ships without third-party imagery.
    [RESOLVED in rev. 2] Real media handling was added: Cloudinary upload /
    delete + product image attach/detach endpoints, `next/image` delivery from
    res.cloudinary.com, and a client upload helper — see section 8.3. Seeded
    products still use deterministic placeholders until an operator uploads
    real product photography (a deliberate choice, not a gap).

3.6 SEO landing pages (the pattern `/{brand}-mobile-price-in-pakistan-{range}`,
    plan §2.2 item 29 and the SeoLandingPage model) were NOT implemented. The
    general category/brand/product SEO surface, dynamic sitemap, JSON-LD and
    robots rules ARE implemented.

3.7 Admin and Vendor have API coverage but NO dedicated admin/vendor UI. The
    admin endpoints exist and are RBAC-protected (verified), and section 2.5 of
    this report lists the public surfaces that ARE built. A Next.js admin panel
    (product CRUD, verification queue with document viewer, installment
    collections, CMS editor) and the vendor dashboard remain to be built.

3.8 Deliberate architectural choice: catalog pages are rendered dynamically
    (`dynamic = 'force-dynamic'`) rather than SSG/ISR. Reason: the build must
    not depend on a live API/DB. Switching the catalog routes to ISR
    (`export const revalidate = 3600`, matching the reference site's
    `s-maxage=3600`) is a one-line change per page once the API is deployed
    alongside the build.

3.9 Recommended additions from the plan that are not implemented: Redis caching,
    BullMQ reminder/payment-due jobs, Sentry, CI/CD pipelines, Docker Compose,
    a full Playwright E2E suite (rev. 2 added targeted real-browser checks for
    responsiveness/branding via puppeteer-core — see section 8.4),
    a payment-gateway adapter layer for JazzCash/EasyPaisa
    (currently admin-confirmed/manual, which matches the reference site's
    consumer-ID collection model), NADRA/eKYC automation, ratings/reviews write
    path,    coupons, admin/vendor image-upload UI screens (the upload API + client
    helper exist and are verified), Urdu locale routing (bilingual content IS
    present inside CMS blocks). Multi-image galleries ARE supported by the data
    model and the attach endpoint (products hold an ordered image array).

3.10 Tooling notes: because no local `mongod` was usable at build time, the test
    harness prefers mongodb-memory-server and otherwise falls back to an isolated
    `<db>_test` database derived from MONGO_URI (dropped afterwards). No
    third-party/system packages were installed, and nothing outside the project
    root was modified.

5.5 Defects found by verification and fixed (not worked around)
    a) `mongoose.connect()` resolved even with no reachable server, so the API
       logged "MongoDB connected" while every query failed. Fixed in
       config/db.ts: verify readyState === 1 and ping admin before reporting
       success, plus connection error/disconnect listeners, and a real
       /health db status (this is now reported honestly as "degraded").
    b) The state machine allowed cancelling a shipment already in `processing`.
       Fixed in the engine (cancel only before processing) to match the
       business rule; unit test asserting the rule now passes.
    c) Illegal order transitions surfaced as HTTP 500. Fixed by mapping them to
       409 CONFLICT in the admin routes (test updated to assert 409 + code).
    d) A Mongoose deprecation (`new: true` on findOneAndUpdate for the order
       counter) replaced with `returnDocument: 'after'`.
    e) Type-safety issues found by `tsc` (lean() typings on populated refs,
       possibly-null subdocuments, a zod-enum ordering bug) were fixed in place
       rather than cast away, plus a void-truthiness bug in the filter sidebar's
       Clear button (now a proper clearFilters() handler).
    f) ESLint flagged setState-in-effect in three client components
       (Deals of the Day countdown, checkout success page, account dashboard).
       Fixed idiomatically: auth is now a small external store consumed through
       useSyncExternalStore (with save/clear notifications), the countdown reads
       a bucketed clock snapshot, and sessionStorage is read through
       useSyncExternalStore — all hydration-safe, no suppressions.

5.6 Limitations of this verification
    - Interactive browser behaviour (client-side JS: add-to-cart, checkout form
      submission, accordions) was verified through the same HTTP interfaces the
      browser uses (Next proxy + API) and via server-rendered HTML. REV. 2
      additionally drives the locally installed Chrome through puppeteer-core
      for layout/theme assertions (section 8.4), but a full click-through E2E
      suite (Playwright) is still not part of the repo. Recommend adding it.
    - mongodb-memory-server could not start on this machine (missing

    - No Lighthouse/performance run was performed; no load testing. Rev. 2 did
      measure real-browser rendering at 8 viewport widths (overflow/layout),
      which is layout correctness, not a performance benchmark.
    - The demo database now contains the seed data plus verification artifacts

8.1 Brand name — "Qist Store"
--------------------------------------------------------------------------------
The requirement was to move off the "qist bazaar" naming and use "Qist Store".
A controlled sweep updated prose/UI/metadata while deliberately preserving every
identifier that must stay machine-stable:

  RENAMED  : page titles/metadata, header + footer wordmark, email copy, CMS and

  PRESERVED: package name `qiststore`, npm workspace names, Mongo database name,
             email addresses (support@qiststore.example), env keys, the CDN
             folder (qiststore/products), API paths and the order-ID prefix
             (QST-…). Renaming those would break runtime config or data, not
             branding.

9.1 Scope and the one thing that was refused
--------------------------------------------------------------------------------
Requested: (a) download and copy every asset from qistbazaar.pk into this
project, (b) replace all emoji with modern React icons, (c) 100% responsive,
(d) redesign the UI/UX after the two reference screenshots.

(a) was DECLINED and is deliberately not done. The reference site's images,
banners, logos and copy are its owners' intellectual property; copying them
would be infringement and would also break this project's own documented policy
(plan.md "Legal note" and README §13 — original assets only). The engineering
path offered instead: keep the owner's own logo/banner assets, serve product
media through the already-integrated Cloudinary pipeline, and take only the
*layout language* of the reference screenshots (which is what (d) did).

(b), (c), (d) were implemented in full and verified.

9.2 Emoji -> react-icons (client 5.7.0, Lucide + Font Awesome sets)
--------------------------------------------------------------------------------

MONGO category seed, which stored emoji glyphs in the icon field). Result: 0
remaining (verified by re-scan over client/src + server/src).
